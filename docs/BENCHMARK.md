# Reconciliation Benchmark Specification & Results (Stage 12B)

## 1. Purpose
This benchmark establishes a controlled, reproducible, and auditable 100-record reconciliation benchmark for the **AI Finance Controller**, aligned with the **Buildathon Track 04** criteria:
1. Benchmark volume exceeding 50 records (100 records generated).
2. Measured match rate vs exception rate.
3. Multiclass classification accuracy and exception-level correctness.
4. Binary detection metrics (True/False Positives/Negatives, Precision, Recall, F1).
5. In-memory throughput measurement (records per second).
6. Honest exception breakdown across financial discrepancy dimensions.
7. Pure deterministic reproducibility.
8. Explicit data provenance.
9. Independent ground truth segregated from matcher execution.
10. Strict zero database writes during benchmark execution.

---

## 2. Dataset Provenance & Integrity Statements
- **Synthetic Benchmark**: All transaction records in this benchmark are deterministically generated by `scripts/generate_benchmark.py`.
- **Not Razorpay Production Data**: No production customer data, live merchant credentials, or real banking feeds are utilized.
- **Not IBM AML 3-Way Counterparts**: The benchmark does **not** claim that IBM AML-Data provided payment, bank, and ledger counterparts. The three legs (`payment`, `bank`, `ledger`) are derived synthetic counterparts generated from canonical transactions with controlled perturbations.
- **Dataset Version**: `BENCHMARK_V1` / `v1.0`. Every row includes embedded JSON provenance metadata in its raw record payload:
  ```json
  {
    "provenance": {
      "source": "SYNTHETIC_BENCHMARK",
      "dataset_version": "v1.0",
      "seed": 42,
      "record_index": 1,
      "derivation": "controlled_perturbation"
    }
  }
  ```

## 3. Architecture & Matcher Isolation

```
      benchmark source (scripts/generate_benchmark.py)
                           ↓
             canonical transaction (BM-001..BM-100)
                           ↓
           ┌───────────────┼───────────────┐
           ↓               ↓               ↓
      payment CSV      bank CSV       ledger CSV
           │               │               │
           └───────────────┼───────────────┘
                           ↓
      controlled perturbation & independent ground truth
                           ↓
             data/benchmark_ground_truth.json
```

### Matcher Execution Flow
1. The benchmark runner (`scripts/run_benchmark.py`) loads records from `benchmark_payment.csv`, `benchmark_bank.csv`, and `benchmark_ledger.csv` using the standard production loader (`load_records`) and normalizer (`normalize_records`).
2. The deterministic reconciliation engine (`app/matching.py::match_records`) receives **only** the normalized records.
3. **Ground truth is never passed to or readable by the reconciliation engine**.
4. The benchmark runner loads `benchmark_ground_truth.json` **strictly after** `match_records()` has completed execution.
5. Evaluation is performed by `app/benchmark_reporting.py::evaluate_benchmark`.
6. **Zero Database Writes**: Benchmark execution runs completely in-memory without invoking SQLAlchemy sessions, migrations, or database repositories.

## 5. Metrics Definitions

### Volume Metrics
- **Total Records**: Total distinct transactions evaluated ($N = 100$).
- **Matched Records**: Transactions where all three sources match perfectly ($M = 40$).
- **Exception Records**: Transactions exhibiting a financial discrepancy or missing leg ($E = 60$).
- **Match Rate**: $\frac{M}{N} \times 100 = 40.0\%$.
- **Exception Rate**: $\frac{E}{N} \times 100 = 60.0\%$.

### Binary Classification Metrics (Matched vs Exception)
- **Positive Label**: `matched` (clean transaction)
- **Negative Label**: `exception` (discrepancy or unresolved)
- **True Positive (TP)**: Expected matched and predicted matched.
- **False Positive (FP)**: Expected exception but predicted matched.
- **False Negative (FN)**: Expected matched but predicted exception.
- **True Negative (TN)**: Expected exception and predicted exception.
- **Precision**: $\frac{TP}{TP + FP}$
- **Recall**: $\frac{TP}{TP + FN}$
- **F1 Score**: $2 \times \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}$

### Multiclass Classification & Exception Accuracy
- **Multiclass Accuracy**: Proportion of records where predicted class (`matched`, `amount_mismatch`, `date_mismatch`, `status_mismatch`, `missing_ledger`, `missing_bank`, `missing_payment`, `unresolved`) exactly matches ground truth.
- **Per-Class Metrics**: Precision, Recall, and F1 computed per exception class, accompanied by Macro Precision, Macro Recall, and Macro F1.

### Throughput & Performance
- **Matching Elapsed Time**: Wall-clock time of `match_records()` captured with `time.perf_counter()`.
- **Exclusion**: File I/O, CSV parsing, normalization, and evaluation are explicitly excluded from the throughput calculation.
- **Throughput**: $\frac{\text{Total Records}}{\text{Elapsed Seconds}}$ (records/second).

## 6. Known Matcher Characteristics & Limitations

1. **No Duplicate Detection**:
   The current reconciliation engine indexes records by `exact_match_key(record) = (record.reference_id or record.transaction_id or "").strip()`. If duplicate reference IDs exist within the same file, subsequent records overwrite earlier ones. The benchmark generator guarantees unique reference IDs (`REF0001` .. `REF0100`).
2. **Deterministic Priority Precedence**:
   When multiple fields differ simultaneously across records, the existing matcher enforces a fixed priority:
   `amount_mismatch` > `date_mismatch` > `status_mismatch` > `matched`.
   To measure classification performance cleanly, the synthetic generator introduces isolated, single-dimension perturbations per record.
3. **Strict Decimal Calculations**:
   Monetary calculations across the benchmark suite strictly utilize Python `Decimal` objects formatted to two decimal places (`0.00`), eliminating float rounding errors.

## 7. How to Run the Benchmark

### 1. Generate Synthetic Benchmark Data
```bash
python scripts/generate_benchmark.py --seed 42 --size 100
```
This generates:
- `data/benchmark_payment.csv`
- `data/benchmark_bank.csv`
- `data/benchmark_ledger.csv`
- `data/benchmark_ground_truth.json`

### 2. Execute Benchmark Runner
```bash
python scripts/run_benchmark.py \
  --payment data/benchmark_payment.csv \
  --bank data/benchmark_bank.csv \
  --ledger data/benchmark_ledger.csv \
  --ground-truth data/benchmark_ground_truth.json \
  --output data/benchmark_results.json
```

### 3. Run Automated Benchmark Test Suite
```bash
pytest -q tests/test_benchmark.py
```
