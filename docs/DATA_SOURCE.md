# Data Source Documentation: IBM AML-Data

## Overview
This document provides complete data provenance and lineage documentation for the external financial dataset integrated into the **AI Finance Controller**.

---

## Dataset Identification

| Attribute | Details |
| :--- | :--- |
| **Dataset Name** | IBM AML-Data (Anti-Money Laundering Synthetic Dataset) |
| **Official Source** | [https://github.com/IBM/AML-Data](https://github.com/IBM/AML-Data) |
| **License** | **CDLA-Sharing-1.0** (Community Data License Agreement – Sharing – Version 1.0) |
| **Publisher** | IBM Research |
| **Nature of Data** | Synthetic financial transactions generated by a multi-agent virtual-world model. |

> [!IMPORTANT]
> **Data Provenance & Disclaimer**:
> 1. The IBM AML-Data dataset is **synthetic data** generated for research purposes.
> 2. It is **NOT** actual Razorpay production data, nor does it contain proprietary customer financial records.
> 3. It does **NOT** natively contain direct Razorpay Payment Gateway ↔ Bank Settlement ↔ Internal Ledger 3-way reconciliation tables out of the box.

---

## Why This Dataset Was Selected

1. **Realistic Transaction Dynamics**: Provides multi-agent banking transactions including bank transfers, credit card payments, cheques, and ACH transfers across multiple currencies and bank accounts.
2. **Open Data License**: CDLA-Sharing-1.0 permits open use and data pipelines without violating banking privacy or proprietary merchant NDAs.
3. **Structured Anomaly Signals**: Contains structured financial fields (`Amount Paid`, `Amount Received`, `Is Laundering`, timestamps, currencies) suitable for testing financial data normalization, lineage tracking, and exception classification.

## Dataset Schema & Field Mapping

### Raw IBM AML-Data Fields

| Field Name | Data Type | Description |
| :--- | :--- | :--- |
| `Timestamp` | String / DateTime | Transaction timestamp (`YYYY/MM/DD HH:MM`) |
| `From Bank` | Integer / String | Source bank identifier |
| `Account` | String | Source account identifier |
| `To Bank` | Integer / String | Destination bank identifier |
| `Account.1` | String | Destination account identifier |
| `Amount Received` | Decimal / String | Amount cleared by receiving institution |
| `Receiving Currency` | String (3-letter ISO) | Currency received |
| `Amount Paid` | Decimal / String | Amount debited from paying account |
| `Payment Currency` | String (3-letter ISO) | Currency paid |
| `Payment Format` | String | Channel format (`ACH`, `Wire`, `Credit Card`, `Cheque`) |
| `Is Laundering` | Integer (0 or 1) | Binary anomaly / laundering flag |

## Transformation & Mapping Strategy

```
+-----------------------------------------------------------------------+
|                       Raw IBM AML CSV Record                          |
| (Timestamp, Account, Account.1, Amount Paid, Amount Received, etc.)  |
+-----------------------------------+-----------------------------------+
                                    |
                                    v
+-----------------------------------+-----------------------------------+
| 1. Raw Layer (`raw_transactions`)                                     |
|    - Preserves un-mutated JSON payload + ingestion timestamp           |
|    - Unique Key: source_dataset + source_record_id                    |
+-----------------------------------+-----------------------------------+
                                    |
                                    v
+-----------------------------------+-----------------------------------+
| 2. Normalized Transaction (`transactions`)                            |
|    - transaction_id   = Mapped from source_record_id                  |
|    - amount           = Amount Paid (Decimal / NUMERIC(18,2))        |
|    - currency         = Payment Currency                               |
|    - transaction_date = Normalized Timestamp                           |
|    - status           = FLAGGED_SUSPICIOUS (if Is Laundering=1) else  |
|                         SUCCESS                                       |
|    - reference_id     = Source Account                                 |
|    - customer_id      = Source Account                                 |
|    - order_id         = Destination Account                            |
+-----------------------------------+-----------------------------------+
                                    |
                                    v
+-----------------------------------+-----------------------------------+
| 3. Three-Way Reconciliation Stream Projection                         |
|    - Payment Record  : Amount Paid, status = SUCCESS / FLAGGED         |
|    - Bank Record     : Amount Received, status = POSTED                |
|    - Ledger Record   : Amount Paid, status = PAID                      |
+-----------------------------------------------------------------------+
```

### Raw vs. Derived Fields

| Field | Source Classification | Rationale |
| :--- | :--- | :--- |
| `source_dataset` | **Derived System Meta** | Tagged as `"IBM_AML_DATA"` for multi-source lineage |
| `source_record_id` | **Derived Natural Key** | Extracted from row ID or hash of `(Timestamp, Account, Index)` |
| `amount` | **Mapped Source Field** | Parsed directly from `Amount Paid` as `Decimal` |
| `bank_records.amount` | **Mapped Source Field** | Parsed directly from `Amount Received` |
| `status` | **Mapped / Derived** | Mapped from `Is Laundering` flag (1 -> `FLAGGED_SUSPICIOUS`) |
| `currency` | **Mapped Source Field** | Parsed directly from `Payment Currency` |

> [!NOTE]
> **Field Availability Policy**: For fields genuinely absent in the source dataset (e.g. merchant tax invoice IDs), the system sets them to `NULL` / `None` rather than fabricating artificial data.

## Dataset Limitations & Operational Scope

1. **No Proprietary Merchant Data**: Synthetic bank transfers do not include payment gateway API callback tokens or Razorpay signature hashes.
2. **Reconciliation Adaptation**: To benchmark 3-way financial reconciliation (Payment ↔ Bank ↔ Ledger), the pipeline projects raw records into payment instruction, bank clearing, and ledger accounting views. Variances between `Amount Paid` and `Amount Received` in cross-currency or fee scenarios are preserved faithfully.
